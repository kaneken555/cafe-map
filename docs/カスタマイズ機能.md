## 1. カスタマイズ機能の目的

- マップの見た目（アイコン色など）を **カスタマイズ設定（Custom）として管理**する。
- 1つのカスタマイズ設定を複数マップで使い回せるようにする。
- シェアマップは **閲覧専用** で、見た目は「シェア時点」のスナップショットとして固定する。
- ユーザーが迷わないよう、以下のルールとする：
    - **1つのMapにつきShareMapは1つ**
    - **Share URLは固定**

---

## 2. エンティティと主なフィールド

### 2-1. Custom（カスタマイズ設定）

```
Custom
- id (PK)
- name
- description
- map_style         : string  // "default" | "light" | "dark" | "mono"
- icon_variant      : string  // "pin" | "badge" | "bubble" | "photo"
- icon_color        : string  // HTMLカラーコード（例: #FF5733）
- icon_size         : integer // px単位（24〜96、デフォルト48）
- show_labels       : bool    // 店名ラベルを表示するか（デフォルト: true）
- border_color      : string  // HTMLカラーコード（将来的に使用予定）
- background_color  : string  // HTMLカラーコード（将来的に使用予定）
- created_by_user_id (FK → User)

- is_snapshot       : bool
- is_public         : bool  // プリセット用のみ true
- original_custom_id: FK → Custom (nullable)

- created_at
- updated_at
```

#### 種類

1. **プリセットCustom（管理者作成）**
    - `is_snapshot = false`
    - `is_public = true`
    - 全ユーザーが利用可能
    - うち1つが「システム全体のデフォルト Custom」
2. **ユーザー作成Custom**
    - `is_snapshot = false`
    - `is_public = false`
    - 作成ユーザー専用（公開機能は当面なし）
3. **スナップショットCustom（ShareMap専用）**
    - `is_snapshot = true`
    - `is_public` は基本使わない（公開/非公開は ShareMap 側で管理）
    - `original_custom_id = スナップショット元の Custom.id`
    - ShareMap と **1対1** で紐づく

---

### 2-2. Map（マイマップ）

```
Map
- id
- title
- owner_id   (FK → User)
- custom_id  (FK → Custom)  // 通常用のみ
- ...（他の項目）
```

- `Map.custom_id` は **必ず `is_snapshot = false` の Custom** を指す。
- Map新規作成時は、**システムで決め打ちされたデフォルトのプリセットCustom** を紐づける。
    - 将来的には「ユーザーごとのデフォルトCustom」を持たせる拡張も想定。

---

### 2-3. ShareMap（シェアマップ）

```
ShareMap
- id
- original_map_id (FK → Map)
- creator         (FK → User)
- custom_id       (FK → Custom) // snapshotCustom
- share_uuid
- is_public       : bool  // 公開/非公開
- title
- description
- created_at
- updated_at
```

- `ShareMap.original_map_id`：シェア元のMap（必須）
- `ShareMap.creator`：ShareMapを作成したユーザー（必須）
    - 通常は元Mapの所有者だが、将来的にはMap共有者も作成できる想定
- `ShareMap.custom_id` は **必ず `is_snapshot = true` の Custom**（スナップショット）
- 1つの Map に対して **ShareMap は1つだけ（1Map1ShareMap）**
    - `original_map_id` にユニーク制約を付けるイメージ
- `share_uuid` は **一度作成したら固定（URL固定）**
- `is_public` で公開/非公開を切り替える
    - 公開期限は設けない
    - 非公開にしても ShareMap / snapshotCustom は削除しない

#### Placeデータ（カフェ情報）の扱い

- ShareMap作成時に、元MapのPlaceデータを **スナップショットとしてコピー** する
    - `CafeSharedMapRelation` テーブルで ShareMap と Cafe を紐づける
- 元Mapでカフェを追加/削除しても、ShareMapには **反映されない**
- 完全に「シェア時点の固定」として扱う
- **allow_syncフィールド**：将来的な拡張用として残すが、現時点では使用しない

---

### 2-4. UserCustomRelation（ユーザーとCustomの関係）

```
UserCustomRelation
- id
- user_id   (FK → User)
- custom_id (FK → Custom)
- is_favorite : bool
- (role など必要に応じて)
```

- 現時点での用途は **"お気に入り管理" のみ**。
- カスタマイズ編集の履歴管理は **当面行わない**（将来拡張の余地は残す）。

---

### 2-5. SystemSetting（システム設定）

```
SystemSetting
- id (PK)
- key         : string (unique)
- value       : string
- description : string
- created_at
- updated_at
```

#### 用途

- `key = 'default_custom_id'` で **デフォルトCustomのID** を管理
- `value` には Custom.id を文字列として格納
- 管理画面からデフォルトCustomを変更可能にする

---

## 3. 挙動・フロー

### 3-1. Map作成時

1. **SystemSettingテーブル**から `key = 'default_custom_id'` のレコードを取得し、デフォルトCustomのIDを取得。
2. 新規 Map 作成時に、その `custom_id` を紐づける。
    - 将来は「ユーザーごとのデフォルトCustom（User.default_custom_id）」があればそちらを優先する想定。

---

### 3-2. ShareMap作成（初回シェア）

1. ユーザーが Map 詳細画面で「シェアリンクを作成」を押す。
2. `original_map_id = map.id` の ShareMap を検索。
    - **存在しない場合のみ**、ShareMap作成フローへ進む。
3. Map.custom（通常Custom, `is_snapshot=false`）を取得。
4. その内容をコピーして **スナップショットCustomを新規作成**：
    - `is_snapshot = true`
    - `original_custom_id = Map.custom_id`
5. ShareMap を新規作成：
    - `original_map_id = Map.id`
    - `creator = currentUser`
    - `custom_id = snapshotCustom.id`
    - `share_uuid = 新規発行（UUIDv4）`
    - `is_public = true`
6. **Placeデータをコピー**：
    - 元MapのCafeを取得（`CafeMapRelation`経由）
    - 各Cafeに対して `CafeSharedMapRelation` を作成

---

### 3-3. ShareMapの再シェア（2回目以降の「シェアリンクを作成」）

**方針：1Map1ShareMap & URL固定 & 再シェア時にスナップショット更新**

1. `original_map_id = map.id` の ShareMap を取得（必ず1件）
2. Map.custom（通常Custom）を取得。
3. その内容で **新しいスナップショットCustom** を作成。
4. ShareMap の `custom_id` を新しいスナップショットに更新。
5. **Placeデータを更新**：
    - 既存の `CafeSharedMapRelation` を全て削除
    - 元MapのCafeを取得（`CafeMapRelation`経由）
    - 各Cafeに対して新しい `CafeSharedMapRelation` を作成
6. `is_public = true` にして再公開。
7. （履歴を残さない現仕様では）旧スナップショットCustomは削除してOK。

**この結果：**
- Share URL（`share_uuid`）は **常に同じ**
- ただし **表示される見た目とPlaceデータは最新のMapの状態** になる

---

### 3-4. ShareMapの公開/非公開

- **公開**：`is_public = true`
- **公開停止**：`is_public = false`
    - この場合、ShareMapもスナップショットCustomも削除しない。
    - 将来再公開したり、履歴として参照する可能性を残す。
- ShareMapを完全に削除する場合（仕様として入れるなら）：
    - 紐づくスナップショットCustomも削除してよい（1対1前提）。

---

### 3-5. ユーザー作成Customの新規作成

**作成可能な画面**
1. **カスタマイズ画面**（マップ選択中のみ遷移可能）
   - 既存Customの選択 + 新規作成も可能
   - 新規作成のみ可能（編集は不可）
2. **カスタマイズ管理画面**（追加予定）
   - 新規作成 + 既存Customの編集も可能

**新規作成フロー**
1. ユーザーがカスタマイズ画面で「新規作成」を選択
2. カスタマイズ項目を設定：
   - `name`：カスタマイズ設定名
   - `description`：説明（任意）
   - `icon_color`：アイコン色
   - `border_color`：枠線色
   - `background_color`：背景色
3. 「保存」ボタンを押す
4. 新しいCustomを作成：
   - `is_snapshot = false`
   - `is_public = false`
   - `created_by_user_id = currentUser.id`
5. （カスタマイズ画面から作成した場合）現在選択中のMapの`custom_id`を新しいCustomに更新

---

### 3-6. Customの編集

**編集可否**
- **ユーザー作成Custom**：編集可能
- **プリセットCustom**：編集不可（閲覧のみ）
- **スナップショットCustom**：編集不可（システム管理用）

**編集可能な画面**
- **カスタマイズ管理画面**（追加予定）のみ

**編集フロー**
1. カスタマイズ管理画面で編集対象のCustomを選択
2. カスタマイズ項目を変更（name, description, 各種色）
3. 「保存」ボタンを押す
4. Customを更新

**影響範囲**
- そのCustomを使用している **全てのMapに即座に反映** される
- 編集前に使用中のMap件数を表示して注意喚起することを推奨

---

### 3-7. MapへのCustom適用・変更

**変更可能な画面**
1. **マップ詳細画面**（実装済み）
2. **カスタマイズ画面**（実装済み）

**変更フロー**
1. カスタマイズ画面を開く
2. プリセットCustomまたはマイカスタムから選択、または手動で設定を変更
3. 「保存して閉じる」ボタンを押す
4. 以下のいずれかが実行される：
   - **プリセットCustom選択時**: 選択したCustomを`Map.custom_id`に適用
   - **手動設定変更時**: 新しいCustom「カスタム設定（自動保存）」を自動作成し、`Map.custom_id`に適用
5. フロントエンドの`selectedMap`と`mapList`の両方が更新される

**マップ切り替え時の挙動**
- マップを切り替えると、新しく選択したマップの`custom_id`に基づいてCustom設定を自動取得
- Custom設定がマップ表示に即座に反映される
- `custom_id`がない場合はデフォルト設定にリセット
- Custom設定取得エラー時はデフォルト設定にフォールバック

**選択可能なCustom**
- システムのデフォルトCustom
- その他のプリセットCustom
- 自分が作成したユーザー作成Custom

**実装の詳細**
- **フロントエンド**: `MapCustomizeModal.tsx`
  - `initialCustomId` プロップで現在適用されているCustomを初期表示
  - プリセット選択時: 選択したCustomの設定を読み込んでプレビューに反映
  - 手動変更時: `selectedCustomId`を`null`にリセット
  - 保存時:
    - プリセット選択中: そのCustomを適用
    - 手動変更時: 新規Customを自動作成して適用
  - `onCustomApplied` コールバックで親コンポーネント（Map.tsx）に通知
- **フロントエンド**: `Map.tsx`
  - `useEffect`でマップ切り替え時にCustom設定を取得・適用（依存配列: `[selectedMap?.id, selectedMap?.custom_id]`）
  - `handleCustomApplied`で`selectedMap`と`mapList`の両方を更新
- **バックエンド**: `PATCH /api/maps/:map_id/custom`
  - `custom_id`を受け取り、Map.customを更新
  - 権限チェック: プリセットCustomまたは自分が作成したCustomのみ使用可能

---

### 3-8. 「マイマップとして登録」

ユーザーが ShareMap を見て「マイマップとして登録」したときの挙動：

1. `share_uuid` から ShareMap を取得。
2. `ShareMap.custom`（スナップショットCustom, `is_snapshot=true`）を取得。
3. その内容をコピーして **通常用Custom** を新規作成：
    - `is_snapshot = false`
    - `is_public = false`
    - `original_custom_id = snapshotCustom.id`
    - `created_by_user_id = currentUser.id`
4. 新しい Map を作成：
    - `title = ShareMap.title`（必要に応じてコピー）
    - `custom_id = 上で作成した通常Custom.id`
5. **ユーザーとMapを紐づける**：
    - `MapUserRelation` を作成（`user = currentUser`, `map = 新しいMap`）
6. **Placeデータをコピー**：
    - ShareMapのCafeを取得（`CafeSharedMapRelation`経由）
    - 各Cafeに対して `CafeMapRelation` を作成
7. （必要に応じて）UserCustomRelation に1件追加してお気に入りにしてもよい。

**この結果：**
- ShareMapとMapは **完全に別物** として管理される
- ShareMapは閲覧専用のまま
- ユーザー側は自分のMapとCustomとして **自由に編集可能** になる

## 4. 今後の拡張余地（意識しているポイント）

- **ユーザーごとのデフォルトCustom設定**
    - `User.default_custom_id` を持たせる形で拡張可能。
- **カスタマイズ履歴（バージョン管理）**
    - `ShareMapVersion` のような履歴テーブルで、再シェア時のスナップショットを蓄積する構成に拡張できる。
- **スナップショットのクリーンアップ**
    - 現状は ShareMap削除時のみ一緒に削除する想定。
    - 「非公開かつ一定期間アクセスなし」などの条件で掃除するバッチを入れる余地もある。

## 5. データベース設計の詳細

### 5-1. インデックス・制約

#### ShareMap

- `original_map_id`：UNIQUE制約 + INDEX
    - 1Map1ShareMapを保証
- `share_uuid`：UNIQUE制約 + INDEX
    - URLの一意性を保証し、検索を高速化

#### UserCustomRelation

- `(user_id, custom_id)`：複合UNIQUE制約
    - 同一ユーザーが同じCustomを重複登録することを防ぐ

---

### 5-2. share_uuidのセキュリティ

- **生成方式**：UUIDv4などの推測困難な方式を使用
    - ランダム性が高く、推測や列挙攻撃を防ぐ
- **実装例**：
    - Node.js: `crypto.randomUUID()`
    - PostgreSQL: `gen_random_uuid()`

## 6. 権限管理

### 6-1. ShareMap関連の権限

| 操作 | 権限者 | 備考 |
|------|--------|------|
| **ShareMap作成（初回シェア）** | Map編集可能なユーザー | 個人マップまたはグループマップの編集権限を持つユーザー |
| **ShareMap再シェア** | Map編集可能なユーザー | 既存ShareMapの更新 |
| **公開/非公開切替** | Map編集可能なユーザー | `is_public`の変更 |
| **ShareMapの閲覧** | 誰でも（URLを知っていれば） | `is_public = true`の場合のみ。非公開の場合はアクセス拒否 |
| **ShareMapの削除** | Map編集可能なユーザー（または管理者） | 削除機能を実装する場合 |

#### Map編集権限の判定方法

ユーザーが対象Mapを編集できるかは、以下のいずれかを満たす場合：

1. **個人マップの場合**：
   - `MapUserRelation`テーブルで`user_id = currentUser.id`かつ`map_id = 対象Map.id`のレコードが存在する

2. **グループマップの場合**：
   - `GroupMapRelation`でMapに紐づくGroupを取得
   - `UserGroupRelation`で`user_id = currentUser.id`かつ`group_id = 上記Group.id`のレコードが存在する
   - つまり、**グループに所属しているユーザー全員がそのグループのMapを編集可能**

```python
# Map編集権限チェックの実装例
def can_edit_map(user, map_obj):
    # 個人マップの場合
    if MapUserRelation.objects.filter(user=user, map=map_obj).exists():
        return True

    # グループマップの場合
    group_maps = GroupMapRelation.objects.filter(map=map_obj).values_list('group_id', flat=True)
    if UserGroupRelation.objects.filter(user=user, group_id__in=group_maps).exists():
        return True

    return False
```

#### 非公開ShareMapへのアクセス

- `is_public = false`のShareMapにアクセスした場合：
  - エラーメッセージ：「このマップは非公開です」
  - HTTPステータス：403 Forbidden

### 6-2. Custom関連の権限

| 操作 | 権限者 | 備考 |
|------|--------|------|
| **Custom新規作成** | ログイン中のユーザー全員 | - |
| **Custom編集** | `Custom.created_by_user` | 作成者本人のみ。プリセット・スナップショットは編集不可 |
| **Custom削除** | `Custom.created_by_user` | 作成者本人のみ。プリセット・スナップショットは削除不可 |
| **Custom閲覧** | プリセット：全ユーザー<br>ユーザー作成：作成者のみ | Custom一覧取得時にフィルタリング |
| **MapへのCustom適用** | Map所有者 | プリセットまたは自分が作成したCustomのみ選択可能 |

#### Custom編集・削除時の権限チェック

```python
# 編集・削除前のチェック
if custom.is_snapshot:
    raise PermissionError("スナップショットCustomは編集・削除できません")
if custom.is_public:
    raise PermissionError("プリセットCustomは編集・削除できません")
if custom.created_by_user_id != current_user.id:
    raise PermissionError("他のユーザーが作成したCustomは編集・削除できません")
```

#### Custom一覧取得時のフィルタリング

```python
# GET /api/customs/ の場合
customs = Custom.objects.filter(
    Q(is_public=True) |  # プリセットCustom
    Q(created_by_user_id=current_user.id, is_snapshot=False)  # 自分が作成したCustom（スナップショット除く）
)
```

### 6-3. Map関連の権限（Custom機能追加分）

| 操作 | 権限者 | 備考 |
|------|--------|------|
| **MapのCustom変更** | Map編集可能なユーザー | 個人マップまたはグループマップの編集権限 |
| **Map削除** | Map編集可能なユーザー | 既存の権限チェックに加え、ShareMapも削除 |

#### 注意事項

**グループマップのCustom変更について**
- グループに所属する任意のメンバーがMapのCustomを変更できる
- Customを変更すると、グループの全メンバーに影響する
- 将来的に細かい権限管理が必要な場合は、`UserGroupRelation`に`role`フィールドを追加する想定

## 7. データ整合性・削除時の挙動

### 7-1. Mapの削除時

#### 削除時の挙動

- 紐づくShareMapも **一緒に削除**（カスケード削除）
- ShareMapに紐づくスナップショットCustomも削除

#### 削除前の確認画面

- ShareMapが存在する場合、その旨を明記
- 例：「このマップにはシェアリンクが作成されています。マップを削除すると、シェアリンクも削除され、他のユーザーはアクセスできなくなります。」

---

### 7-2. Customの削除時

#### ユーザー作成Customを削除したとき

**削除時の挙動**
- そのCustomを使用しているMapは **デフォルトCustomに自動変更** される

**削除前の確認画面**
- 使用中のMap件数を表示
- 削除後はデフォルトCustomに変更されることを明記
- 例：「このカスタマイズ設定は3件のマップで使用されています。削除すると、それらのマップはデフォルトのカスタマイズ設定に変更されます。」

#### プリセットCustomの削除（管理者操作）

- 基本的に削除不可（特にデフォルトCustomは削除禁止）
- やむを得ず削除する場合は、使用中のMapを別のプリセットCustomに移行してから削除

### 8-6. 色の仕様

**色コードの形式**
- HTMLカラーコード形式：`#RRGGBB`（6桁の16進数）
- 例：`#FF0000`（赤）、`#00FF00`（緑）、`#0000FF`（青）

**デフォルト色**
- アイコン色：`#FF5733`（オレンジ系）
- 枠線色：`#000000`（黒）
- 背景色：`#FFFFFF`（白）

**カラーピッカー**
- HTML5の`<input type="color">`を使用
- または、React Color、Material-UIのカラーピッカーコンポーネント

**バリデーション**
- 正規表現：`^#[0-9A-Fa-f]{6}$`
- 不正な形式の場合：「正しい色コードを入力してください（例: #FF0000）」

## 10. 環境変数

### 10-1. フロントエンド環境変数

#### VITE_GOOGLE_MAPS_MAP_ID（現在未使用）

**現在の状態**
- この環境変数は**現在使用していません**
- `.env`ファイルでコメントアウトされています

**設定ファイル**
- `frontend_dev/.env`

**現在の設定**
```env
# Google Maps Map ID (現在未使用)
# 注意: mapIdとstylesプロパティは併用できないため、カスタマイズ機能でマップスタイルを
# 動的に変更するため、mapIdは使用していません
# VITE_GOOGLE_MAPS_MAP_ID=
```

**使用していない理由**

Google Maps JavaScript APIには以下の制約があります：
- **mapIdとstylesプロパティは併用できない**
- mapIdを設定すると、マップスタイルはGoogle Cloud Consoleでの管理のみに限定される
- カスタマイズ機能では、ユーザーが動的にマップスタイルを変更できることが必須要件

そのため、以下の技術的判断を行いました：

1. **動的なマップスタイル変更を優先**
   - ユーザーがリアルタイムでマップスタイル（デフォルト/ライト/ダーク/モノトーン）を切り替えられる
   - `styles`プロパティを使用してJSONベースのスタイル定義を適用

2. **Advanced Markersは不要**
   - 当アプリケーションではAdvanced Markersではなく、`OverlayView`を使用してカスタムマーカーを実装
   - mapIdはAdvanced Markersを使用する場合に必要だが、現在の実装では不要

3. **将来的な拡張性の確保**
   - 必要に応じてスタイルJSONファイルを追加・変更できる
   - ユーザーごとのカスタムスタイル保存が可能

**技術的背景**

以下のファイルから`mapId`プロパティを削除しました：
- `frontend_dev/src/components/Map/Map.tsx`（227行目）
  - メインのマップコンポーネント
  - `styles`プロパティのみを使用
- `frontend_dev/src/components/MapCustomizeModal/MapPreview.tsx`（190行目）
  - カスタマイズ画面のプレビュー
  - `styles`プロパティのみを使用

**参考情報**
- Google Maps APIエラー: "A Map's styles property cannot be set when a mapId is present."
- 詳細: [Google Maps Platform ドキュメント](https://developers.google.com/maps/documentation/javascript/styling)
